# Player 보행면 이탈 시 Deck Enemy·Boss 이동 정지 원인과 개선 계획

작성일: 2026-10-06. 현재 작업 폴더의 C++와 구현 문서를 기준으로 분석한 계획이다. 작성 당시에는 코드 구현·PIE·빌드·테스트를 수행하지 않았다.

구현 상태: 2026-10-07 사용자 요청에 따라 공통 추적 해석, 지속적인 난간 지지, 경로/Claim 보존, 제한된 관찰·재시도, 일반 적/Boss 이동·공격·스냅샷·경보 연동을 반영했다. Editor 빌드와 기존 Blueprint/행동 트리의 읽기 검사를 완료했다. 자동화 테스트는 생략했으며 PIE 수동 재현·다중 클라이언트 확인은 아직 수행하지 않았다. 이 문서의 테스트 계획은 수용 기준이며 실행 결과가 아니다. 적용 설정과 남은 수동 확인은 [구현 및 Sight 설정 가이드](../../docs/DeckEnemy_Rail_Tracking_and_Sight_Config.md)를 참조한다.

수정일: 2026-10-07. Player가 난간에 계속 접지해 있는 상황을 핵심 재현 조건으로 반영했다. **난간 체류는 일시적인 공중 상태가 아니다.** 현재 지지면과 HostShip·Surface 관계가 확인되는 동안 계속 갱신되는 추적 상태로 처리한다. 아래 난간 정책은 종전의 짧은 기억 유예를 통한 난간 처리보다 우선하며, 구체적인 질의·목적지 선택 절차와 장시간 검증은 8절을 따른다.

## 1. 결론과 목표

현재는 **적이 안전하게 걸을 바닥을 확인하는 판정**을 **Player를 추적할 기준 위치를 구하는 판정**에도 그대로 사용한다. Player가 점프하거나 난간·장애물 위에 올라가거나 갑판 밖으로 이동하면 타깃의 보행면 판정이 실패한다. 이동 계획과 공격 시작 조건이 함께 실패하고, 기존 경로를 취소하거나 타깃을 해제하는 코드 때문에 적이 멈춘다.

해결 원칙은 다음 세 조건을 분리하는 것이다.

1. **전투 타깃 자격:** Player가 살아 있고 유효하며 인지·영역 정책상 추적 대상인가?
2. **추적 기준:** 적이 어느 갑판 위치를 기준으로 접근·후퇴·측면 이동해야 하는가?
3. **이동·공격 안전:** 적 자신의 이동 경로가 실제 바닥으로 지지되는가? 실제 Player에게 사거리·높이·LOS·타격 조건을 만족하는가?

Player의 착지 여부만으로 이동이나 Combat을 해제하지 않는다. 반대로 적 자신의 바닥, 경로 지지, 목적지 공간, 점유 검증은 유지한다. 안전한 경로가 없는 경우의 대기는 정상 행동이며, 모든 상황에서 계속 걷게 만드는 것이 목표는 아니다.

특히 Player가 걸어 설 수 있는 난간 표면과 적의 캡슐이 이동 가능한 갑판 그래프는 서로 다른 공간이다. Player의 난간 접지를 추적 증거로 사용하되 난간 자체를 적의 이동 그래프에 추가할 필요는 없다. 난간 체류 시간만을 이유로 추적 기준을 만료시키지 않는다.

## 2. 코드에서 확인된 원인

### 2.1 실제 발밑 판정의 범위가 추적에 비해 좁다

`Source/Enemy/Private/DeckAI/DeckWalkAreaComponent.cpp:408`의 `ResolveActorOnDeck`는 ACharacter의 실제 발 위치를 사용한다.

- Walking이고 CurrentFloor가 유효하면 등록된 충돌 컴포넌트와 발바닥 사이의 높이 65 cm, XY 100 cm 이내 조건을 검사한다.
- 실패하면 발 위치의 위 10 cm·아래 65 cm만 탐색한다.
- 실제 바닥을 찾은 뒤 유효한 그래프 노드가 가까워야 성공한다. 기본 CellSize는 75 cm, MaximumStepHeight는 45 cm다. 저장된 BP의 값은 별도 확인이 필요하다.

따라서 Falling 진입 즉시 반드시 실패하는 것은 아니다. 발밑 65 cm 범위 안에 바닥이 있으면 fallback이 성공할 수 있다. 하지만 더 높이 뜨거나 유효 노드가 없는 곳으로 이동하면 실패한다. 이 함수는 스폰·착지·Movement Base·적 자신의 안전한 이동에는 적합하지만, 공중의 Player를 추적하는 일반 질의로는 부족하다.

### 2.2 일반 Deck Enemy의 경로가 취소된다

`Source/Enemy/Private/DeckAI/DeckEnemyNavigationComponent.cpp`

- `PlanTargetDistanceRoute`는 시작하자마자 `CancelCombatRoute`를 호출한다. 이후 Enemy와 Player 모두 `ResolveActorOnDeck`에 성공해야 새 경로를 만든다. 실패하면 기존 경로도 이미 사라져 있다.
- `ReplanIfTargetMoved`는 Player 보행면 판정 실패 시 `CancelCombatRoute`를 호출한다. 기존 경로가 안전해도 Player의 일시적인 공중 상태만으로 제거한다.
- 거리 계산에도 실제 Player 발 위치의 Z를 사용한다. 보행면 실패 조건만 제거해도 공중의 Z가 목적지 투영에 들어가 새 경로 선택이 실패할 수 있다.

`Source/Enemy/Private/Task/BTT_MoveToDeckWaypoint.cpp`는 이 재계획을 이동 Tick에서 호출한다. 경로가 없어지면 Route가 실패하고 `StopDeckMove`가 `StopMovementImmediately`를 호출한다. 쿨타임 측면 이동 Task인 `BTT_MoveAroundDeckTarget`도 같은 계획 함수를 사용하고 실패 시 경로와 이동을 정리한다.

즉 일반 적의 대표 흐름은 다음과 같다.

```text
Player의 발밑 보행면을 찾지 못함
→ 재계획 실패 / 기존 경로 삭제
→ Route Tick 또는 이동 Task 실패
→ StopMovementImmediately
→ 새 목적지도 선택하지 못해 대기·실패 반복
```

기존 재계획 제한 때문에 취소 시점에는 지연이 있을 수 있다. 모든 정지가 정확히 같은 프레임에 발생한다고 단정하지 않는다.

### 2.3 목적지 선택 실패가 타깃 상태까지 건드린다

`Source/Enemy/Private/Task/BTT_SelectDeckWaypoint.cpp:58`은 Player 보행면 판정 실패 시 `Enemy->ClearCombatTarget()`을 호출한다.

이 호출은 `ARangedEnemy`의 내부 `CombatTarget`을 비운다. Controller의 캐시와 Blackboard를 함께 비우는 `ABaseAIController::ClearCombatTarget` 호출과는 다르다. 따라서 Controller·Blackboard에는 Player가 남아 있는데 Enemy 내부에는 없는 상태가 될 수 있다. 이후 이동·공격이 서로 다른 타깃 상태를 보게 된다.

보행면 질의 실패는 타깃 사망·제거와 구분해야 하며, 타깃 변경과 해제는 Controller가 소유하도록 통일해야 한다.

### 2.4 보스도 목적지 선택 진입 조건이 같은 문제를 가진다

- `Source/Enemy/Private/BossAI/BossDeckPointSelector.cpp:96`: 일반 Walk/Dash/Vanish 목적지 선택 전에 Boss와 Player의 보행면 판정을 모두 요구한다. Vanish도 이 공통 진입 조건을 통과해야 한다.
- `Source/Enemy/Private/Task/BTT_SelectBossDestinationPoint.cpp`: 선택 실패 시 Blackboard 목적지와 `Boss->ClearDestination()`을 정리한다. Walk Route와 Claim도 해제된다. 단, Boss Busy 상태에서는 확정된 능력의 목적지를 건드리지 않도록 기존 보호 코드가 있다.
- `Source/Enemy/Private/Task/BTT_BossStrafe.cpp:55`: 시작 시 Player 보행면 성공과 같은 Surface를 요구한다. 이미 실행 중인 짧은 Strafe는 Player의 보행면을 매 Tick 재검사하지 않으므로, 점프가 모든 보스 이동을 즉시 끊는다고 일반화할 수는 없다.

보스의 기존 고정 Walk Route 역시 Player를 항상 추적하는 구조는 아니다. 실제로 어느 분기의 실패·Abort가 관찰된 정지를 발생시키는지는 보스별 BT 실행 기록으로 확정해야 한다.

### 2.5 공격 분기도 함께 닫힌다

- `DeckEnemyCombatComponent.cpp:90`의 `EvaluateAttack`
- `DeckRangedEnemy.cpp:265`의 `EvaluateAttackTarget`
- `BossAttackPositionLibrary.cpp:19`의 근접 공격 시작 판정

이 경로들은 Player의 실제 보행면과 같은 Surface를 요구한다. 이동도 실패하고 공격도 불가능해지면서 대기만 하는 현상이 더 뚜렷해진다. BT Decorator만 완화하면 실제 Ability의 시작 판정에서 다시 거절될 수 있으므로 두 계층을 함께 점검해야 한다.

### 2.6 보스 스냅샷에 부분적인 공중 처리만 있다

`Source/Enemy/Private/GAS/Tasks/AbilityTask_BossTargetSnapshot.cpp:50`의 `SamplePose`는 과거 유효 스냅샷이 있으면 공중에서도 이전 갑판 Z와 Surface를 유지하며 Player XY를 갱신한다.

이는 활용할 수 있는 기존 방향이다. 다만 첫 샘플부터 Player가 공중이면 초기 스냅샷을 만들지 못하고, 일반 Walk·Strafe·기본 목적지 선택과 Deck Enemy에서는 공유하지 않는다. 또한 이 스냅샷은 이동 가능한 위치 핸들 자체가 아니므로 목적지와 돌진 구간 검증은 여전히 필요하다. 사망 시 스냅샷을 고정하는 현재 계약도 보존해야 한다.

## 4. 설계안

### 4.1 엄격한 자기 바닥 질의는 유지하고 추적 전용 질의를 추가한다

`ResolveActorOnDeck`의 65 cm 제한을 전역적으로 늘리는 방식은 사용하지 않는다. Movement Base·스폰·적 자신의 바닥 검증까지 공중 위치나 잘못된 층을 바닥으로 인정하게 될 수 있기 때문이다.

공유 타입과 `UDeckCombatTargetResolverComponent`를 추가하는 안을 권장한다. 일반 Deck Enemy와 ShipBossEnemy가 각각 소유하며, 두 계열이 동일한 질의·기억 정책을 사용한다. 보행면의 공간 질의는 `UDeckWalkAreaComponent`에, 타깃별 기억과 수명은 새 컴포넌트에 둔다. 함수명·필드명은 구현 단계의 제안이다.

추적 결과에는 다음을 분리해 담는다.

- Target와 HostShip의 약한 참조, 최근 **확정 바닥**과 확정 시각
- Player의 현재 실제 World/Local 위치와 실제 발 위치
- 추적용 Local XY·Surface·바닥 높이, 필요할 경우 새 Revision의 보행면 핸들
- 해석 출처: 실제 갑판 바닥 / 함선 장애물 위 접지 / 공중 투영 / 최근 위치 / 경계 후보 / 해결 실패
- 실제 접지 여부, 표면 식별의 확실성, 실패 사유

난간·장애물 지지 컴포넌트와 지지점, 현재 증거 확인 시각도 보관한다. 같은 난간 위 현재 접지 확인으로 갱신되는 시각과 마지막 실제 갑판 접지 시각을 분리한다. 현재 지지가 확인되는 상태를 과거 갑판 위치의 기억으로 분류하지 않는다.

`FDeckWalkLocation`은 실제 검증된 이동 위치에만 사용한다. 공중 Player의 실제 좌표나 그래프 밖 XY를 넣어 유효한 이동 핸들처럼 취급하지 않는다. 타깃의 위치, 추적 중심, 적의 최종 목적지를 서로 다른 값으로 관리한다.

### 4.2 해석 우선순위와 층 선택

1. 실제 바닥 판정이 성공하면 최근 확정 바닥을 갱신한다. 다만 근접 fallback 성공과 CharacterMovement의 실제 접지는 별도 표시한다.
2. 갑판 그래프 판정에 실패했더라도 Player가 난간·장애물에 접지해 있으면 현재 지지 컴포넌트·지지점·Movement Base의 HostShip 관계를 확인한다. 연관 Surface를 공간 질의로 식별하고 현재 XY를 사용해 추적 기준을 계속 갱신한다. 갑판 바로 아래의 투영점이 막혀 있으면 적의 도달 가능한 주변 노드를 찾는다. 이 상태에는 공중 기억 유예를 적용하지 않는다.
3. 현재 지지가 없는 일시적인 공중 상태이면 최근 확정 Surface를 우선한다. 현재 XY를 그 층의 검증된 바닥에 투영하고, 실제 공중 Z를 이동 목표 높이로 사용하지 않는다. 투영과 현재 증거가 모두 부족하면 짧은 유예 동안 최근 유효 기준이나 아직 안전한 기존 경로를 사용한다. 공중 샘플만으로 최근 확정 시각을 계속 갱신하지 않는다.
4. 첫 발견부터 공중인 경우, 제한된 높이·XY 범위에서 해당 HostShip의 실제 바닥을 탐색한다. 다른 배의 Movement Base, 등록되지 않은 바닥, 층을 가로막는 충돌, 중복 후보를 확인한다. 위·아래층의 선택이 모호하면 실패 사유를 반환한다.
5. 새 층의 실제 접지가 확인되면 이전 Surface 기억을 교체한다. 공중에서 높이가 다른 층에 가까워졌다는 이유만으로 Surface를 바꾸지 않는다.
6. 같은 층 투영 실패 시 도달 가능한 노드의 경계 후보를 제한 거리 안에서 찾는다. 후보는 경로·캡슐 여유·Claim까지 만족해야 한다.

기억 유예 1.0초는 현재 지지·투영 증거를 잃었을 때의 초기 튜닝 후보이며 난간 체류 제한 시간이 아니다. 재시도 0.2~0.3초도 확정 수치로 간주하지 않는다. 실제 점프·롤·넉백의 체공 시간과 함선 크기를 측정해 정한다. 기존 재계획 거리 100 cm·최소 간격 0.35초는 먼저 유지한다. 공중 투영의 수직 범위와 난간 주변 탐색 허용 거리는 별도 설정으로 둔다.

### 4.3 새 경로가 준비되기 전 기존 경로를 제거하지 않는다

`PlanTargetDistanceRoute`를 다음 순서로 바꾼다.

```text
타깃 자격 확인
→ 추적 기준 해석
→ 후보 목적지와 경로를 임시 결과로 계산
→ 바닥·경로·공간·점유 검증
→ 새 Claim과 경로 교체 성공 시 기존 Claim 정리
```

현재 `ClaimGoal`, `SetLocationGoal`, `SetLocationGoalInDistanceBand`도 실패 시 기존 상태를 지우므로 호출부 순서만 바꿔서는 충분하지 않다. `TryReplaceGoal` 성격의 경로 교체 API와 동일 소유자의 Claim 교체를 함께 설계한다. 실패하면 아직 유효한 이전 Route·Claim을 보존하고, 성공 시에는 경로와 예약이 일치하게 갱신한다. 서버의 한 실행 흐름에서 이 교체를 처리한다.

보존에는 한계가 있다. 적 사망·Frozen, HostShip 변경, 그래프 Revision 변경, 기존 경로의 바닥·목적지 무효, 명시적인 전투 종료에서는 이전 경로를 즉시 정리한다. 새 타깃을 획득했을 때 이전 Player를 향한 경로를 무조건 유지하지 않는다.

거리 이동은 추적 바닥 Z와 현재 Player XY를 기준으로 기존 Player–Enemy 선 공식을 유지한다. 측면 이동은 동일한 추적 중심을 공유하되 기존 거리 띠와 경로 지지 검증을 유지한다. 바깥쪽 XY로 인해 거리 띠 경로가 불가능하면 일반 안전 접근 또는 관찰로 전환하고 실패 재실행을 반복하지 않는다.

### 4.4 타깃·상위 상태는 Controller가 일관되게 관리한다

- `BTT_SelectDeckWaypoint`에서 단순 보행면 실패 때문에 Enemy 내부 타깃을 비우는 코드를 제거한다.
- 보행면 해석 실패는 `TransientUnresolved`, `NoReachableGoal`, `DifferentSurfaceUnreachable` 등으로 구분해 BT에 전달한다.
- Player 사망·파괴, 실제 인지 상실, Territory 이탈, 명시적 타깃 변경은 기존 Controller 경로로 처리한다.
- 임시 실패 시 Focus와 타깃을 유지하고 안전한 기존 경로를 수행한다. 기존 경로가 없거나 완료되면 제한된 재시도·관찰을 수행한다.
- 현재 증거를 잃은 장기 이탈에는 최근 배 로컬 지점 조사 또는 Passive 복귀를 명시적으로 선택한다. 난간 지지와 인지·영역 조건이 유지되지만 근접 공격 위치가 없는 상황은 Combat 관찰/가능한 재배치로 처리하며 기억 만료로 Passive에 보내지 않는다. 조사 후에는 직접 Sight로 확인해야 다시 Combat으로 진입하며, 기억만으로 Player를 재획득하지 않는다.

이동 선택 실패를 전투 종료와 동의어로 사용하지 않는다. 현재 난간 지지가 유지되는 것과 현재 증거 없이 과거 위치만 무기한 사용하는 것을 구분한다. 인지 상실·사망·영역 이탈에 대한 기존 종료 정책은 유지한다.

### 4.5 보스 경로에 공통 해석을 적용한다

- `BossDeckPointSelector::SelectDestinationLocation`: Boss 자신의 엄격한 바닥 판정은 유지하고, Player 쪽 조건을 공유 추적 결과로 교체한다. Walk·Dash·Vanish의 후보 필터와 최종 안전 검증은 유지한다.
- `BTT_BossStrafe`: 같은 Surface의 확실한 추적 기준으로 시작할 수 있게 한다. 진행 중 Boss 자신의 바닥·앞쪽 지지·공간 검사와 짧은 실행 시간은 유지한다.
- `BTT_SelectBossDestinationPoint`: 임시 해석 실패만으로 유효한 기존 목적지를 지우지 않도록 한다. 이미 목적지가 무효하거나 상위 상태가 바뀌었다면 정리한다.
- `AbilityTask_BossTargetSnapshot`: 공유 해석으로 첫 공중 샘플도 처리하고, 스냅샷에는 해석 출처·Surface를 반영한다. 사망 시 Freeze, 확정 공격의 로컬 위치·방향 계약은 보존한다.
- Chain Slash Dash·Chain Vanish: 같은 결과를 사용하되 기존 “Player 뒤” 관계와 고정 거리, 같은 층, 연속 지지 구간, 장애물 Sweep 검증을 유지한다.
- Dash 경로가 실제로 없으면 해당 스킬만 실패시키고 Walk·Strafe·관찰 같은 다른 분기로 이어지게 한다. 투영 위치를 향해 바다나 벽을 통과하는 돌진은 허용하지 않는다.
- `State_Boss_Busy` 동안 BT가 확정된 능력 목적지를 바꾸지 않는 보호는 그대로 유지한다.

### 4.6 공격 정책은 이동 수정과 분리해 검증한다

첫 적용에서는 이동 정지 수정과 타깃 상태 일관성을 먼저 검증하고 기존 공격 거리·쿨다운·피해 수치를 유지한다. 그 다음 동일한 추적 해석을 공격 시작 조건에 연결한다.

- 근접: Player의 실제 착지를 필수 조건으로 삼지 않되, 신뢰할 수 있는 같은 층 관계와 실제 3D 거리·높이·LOS를 요구한다. 피해는 실제 무기 타격 영역으로 판정한다. 투영한 바닥 위치에 Player가 있는 것처럼 피해를 계산하지 않는다.
- 원거리: 같은 갑판 위의 공중 Player는 실제 조준점과 거리·LOS로 판정한다. 다른 층·다른 배까지 공격을 확대하는 정책은 이번 기본 적용에서 활성화하지 않는다.
- 보스 기본 공격: `BossAttackPositionLibrary`와 실제 Ability 시작 조건을 같은 정책으로 맞춘다. 근접 타격 영역과 LOS를 유지한다.
- 확정 공격: Player의 일시적인 바닥 이탈 때문에 이미 Commit한 몽타주·돌진을 취소하지 않는다. 기존 사망·Frozen·스킬별 취소 조건과 종료 후 판단 적용은 유지한다.

`EvaluateAttack`, `EvaluateAttackTarget`, BT Decorator, GAS의 CanActivate/Commit 전 검사까지 확인하여 “BT에서는 Ready인데 Ability가 매번 실패”하는 불일치를 없앤다.

### 4.7 경보·LOS 복구·기타 추적 경로도 연결한다

- `EnemyAlarmComponent::EmitAlarm`은 공중 타깃에서도 해석된 당시 배 로컬 위치를 스냅샷으로 저장할 수 있게 한다. 발신 후 스냅샷이 Player를 따라 움직이지 않게 한다.
- `DeckEnemyCombatComponent::RecordBlockedLOS`는 공유 해석으로 실패 시점의 기준을 저장한다. 공중이라는 이유만으로 복구 상태를 버리지 않는다.
- `DeckWalkRouteComponent::SetActorGoal`과 `bTrackTarget` 분기도 추적 전용 질의를 사용하거나 사용처가 없으면 별도로 정리한다. 고정 위치 Route의 자기 바닥 검증은 유지한다.
- 조사 지점이 도달 불가이면 제한된 안전 대체점 또는 조사 종료를 선택한다. 위치를 임의의 다른 층으로 옮기지 않는다.

### 4.8 수명·네트워크·비용

해석·기억·목적지 선택·Claim은 서버만 수행한다. 클라이언트는 기존 CharacterMovement와 능력 연출 복제를 사용하며, 새 추적 캐시 전체를 복제하지 않는다.

타깃 교체·해제, Enemy/Boss 사망, 풀 복귀·재활성화, HostShip 변경·파괴 시 기억과 재시도 타이머를 초기화한다. Revision 변경 시 이전 NodeIndex를 사용하지 않고 저장 LocalFloor·Surface를 제한 범위에서 재해석한다. 만료된 기억을 Rebuild로 되살리지 않는다.

한 판단 주기 안에서는 일반 이동·공격·보스 스냅샷이 같은 해석 결과를 재사용한다. 비용이 큰 투영과 도달 가능 후보 탐색을 모든 Task에서 매 프레임 중복 실행하지 않는다. 실패 로그는 상태 변경 또는 재시도 제한 주기에만 출력한다.

## 5. 구현 순서와 산출물

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 재현·진단 | 일반 Melee/Ranged, 활성 보스별 실제 BT 연결·Abort 설정 확인. 점프 전후 타깃/Surface/Route 기록 | 어떤 호출이 경로·타깃을 지우는지 실행 기록으로 확정 |
| 2. 공유 해석 | 새 결과 타입·컴포넌트·난간 지지 질의와 Surface 연계, 투영·주변 후보, 기억·만료·첫 샘플 처리 | 갑판·지속적인 난간 접지·공중·모호한 층·갑판 밖을 구분 |
| 3. 일반 적 이동 | 경로/Claim 교체 API, Navigation·Select Task·측면 이동·타깃 관리 수정 | 점프만으로 경로·CombatTarget을 잃지 않음 |
| 4. 보스 이동 | 목적지 선택·Strafe·스냅샷·Chain 경로 연결 | 각 보스가 공중 타깃에도 안전한 이동 또는 관찰 선택 |
| 5. 전투 연계 | 공격 시작 조건의 일관성, 경보·LOS 복구·ActorGoal 연결 | 공중 추적과 실제 공격 조건이 모순되지 않음 |
| 6. 에셋·문서 | 실제 BehaviorSet와 BT의 fallback·재시도·Abort 반영. 설정 설명 업데이트 | 기존 트리 사용자 설정을 보존하며 새 정책 적용 |
| 7. 검증 | Editor 빌드, 핵심 자동화 회귀, PIE와 서버/클라이언트 확인 | 아래 수용 기준 충족 |

기본 수정 대상은 `DeckWalkAreaComponent`, `DeckWalkTypes`, 새 Resolver, `DeckEnemyNavigationComponent`, `DeckWalkRouteComponent`, `DeckEnemyCombatComponent`, `DeckRangedEnemy`, `BaseAIController`의 상태 연계, 관련 Deck/보스 Task·Selector·Snapshot·Alarm이다.

실제 적용 에셋은 `DA_DeckMeleeEnemy_AI`, `DA_DeckRangedEnemy_AI`, 각 보스 BehaviorSet, DeckCombat 트리와 현재 연결된 보스 서브트리에서 확인한다. 코드의 AuthoringCommandlet 구조가 모든 저장 BT에 그대로 적용되어 있다고 가정하지 않는다. `-RebuildGenerated`로 트리를 일괄 초기화하지 않고 필요한 분기·설정만 수정한다.

## 6. 진단과 검증 계획

### 6.1 진단 표시

같은 기록에 Enemy/Boss 이름, HostShip, Target, AI State, 실제 이동 모드, 실제 발 위치, 확정 Surface, 추적 출처·나이, 경로 목표·Revision, 재계획 결과와 정지 사유를 남긴다. 타깃 해제 기록에는 발신 계층을 표시한다.

디버그 표시에서는 Player 실제 위치, 추적 투영점, 최종 목적지와 경로를 다른 색으로 그린다. 실패 사유는 최소한 타깃 무효·자기 바닥 없음·임시 타깃 바닥 없음·투영 모호·층간 미연결·바닥 지지 없음·점유·Revision 변경으로 구분한다.

### 6.2 기능 검증표

| 장면 | 기대 결과 |
| --- | --- |
| 제자리·이동 점프, 연속 점프 | 타깃 참조와 안전한 경로 유지. 점프 Z만으로 취소·재계획하지 않음 |
| 처음 발견한 Player가 공중 | 명확한 투영 또는 관찰·재시도. 영구 실패 루프 없음 |
| 난간·상자 위로 이동 후 60초 이상 머무름 | 현재 지지에 따른 추적 유지. 유예 만료로 경로·타깃을 잃지 않음. 장애물 관통·가짜 근접 명중 없음 |
| 처음 발견한 Player가 난간 위 | 과거 갑판 접지 이력 없이 올바른 함선·Surface와 안전한 후보 선택 |
| 난간 바로 아래에 유효 그래프 노드가 없음 | 갑판 안쪽 후보 접근. 수직 투영 실패만으로 전체 전투 루프 실패하지 않음 |
| 갑판 가장자리, 배 밖 낙하, 다른 배 이동 | 한정된 경계/최근 지점까지만 이동 후 정책에 따라 종료 |
| 위·아래층의 같은 XY | Surface 오선택 없음. 연결되지 않은 층으로 순간 이동·직선 이동하지 않음 |
| 배 이동·회전·Pitch/Roll 중 점프 | 배 로컬 추적과 경로 유지, Movement Base는 적의 실제 바닥 |
| 안전한 기존 경로가 있는데 새 계획 실패 | 기존 Route·Claim 보존. 새 경로 성공 시 일관되게 교체 |
| 기존 경로 자체의 바닥·목적지가 무효 | 안전하게 정지하고 이유 기록. 낡은 경로 강제 실행 없음 |
| 그래프 Rebuild | 이전 핸들 사용 금지, 유효 기억만 새 Revision에 재해석 |
| Player 교체·사망·제거, 적 Frozen·사망·풀 재사용 | 타깃·기억·예약·Focus 정리. 확정 공격 수명 계약 유지 |
| 다수 적이 같은 경계 지점을 원함 | Claim 충돌 처리, 안전 대체점·제한 재시도 |
| 보스 Walk/Strafe/Dash/Vanish/Chain | 공중 해석 공유, 스킬별 경로 안전과 Busy 보호 유지 |
| 서버와 클라이언트 2개 | 서버 판단 일치, 이동·공격·피해 중복 없음 |

자동화 검증은 핵심 정책 회귀에 집중한다. 공중 샘플의 마지막 Surface 유지와 만료, 첫 샘플 투영과 다층 거절, 재계획 실패 시 기존 Route·Claim 보존, 타깃/풀/Revision 변경 정리를 검증한다. 실제 충돌 바닥이 있는 월드에서 보행면 해석을 확인하여 계산식만 그대로 따라 하는 테스트를 피한다. 기존 Deck·Boss 테스트는 현재 구조와 호환되는 항목을 선별한다.

### 6.3 최종 수용 기준

1. 적 자신이 유효한 바닥과 경로를 가진 상태에서는 Player의 일시적인 공중 상태만으로 경로를 삭제하거나 타깃을 해제하지 않는다.
2. Player 실제 위치·추적 기준·최종 이동 목적지가 구분되어 잘못된 공중 Z나 그래프 밖 좌표가 이동 핸들로 쓰이지 않는다.
3. 목적지를 바꾸지 못해도 기존 안전 경로를 유지한다. 기존 경로가 무효하면 정지한다.
4. 난간의 현재 지지가 확인되는 동안에는 체류 시간으로 추적을 종료하지 않는다. 현재 증거를 잃은 장기 이탈·연결되지 않은 층·다른 배에는 명시적인 관찰·조사·복귀가 있으며 무한 실패 반복이 없다.
5. 난간·구멍·벽·층간 충돌·점유 검증과 실제 피해 판정은 유지한다.
6. 일반 적과 모든 적용 보스의 BT/Ability 시작 판정이 일치하고, 기존 확정 공격과 네트워크 계약이 보존된다.

## 7. 피해야 할 단순 수정과 남은 확인 사항

- 보행면의 높이 범위만 크게 늘리거나 `ResolveActorOnDeck`의 탐색 높이를 전역적으로 확대하지 않는다. 자기 바닥과 층 판정을 망가뜨릴 수 있다.
- Player의 월드 위치를 곧바로 AddMovementInput·일반 MoveTo·SetActorLocation으로 따라가지 않는다. 움직이는 배의 로컬 경로와 안전 검증을 우회한다.
- Surface 확인을 전부 제거하거나 직선 돌진·Vanish로 도달 불가 경로를 대체하지 않는다.
- 마지막 바닥 위치를 무기한 기억하지 않는다. Player가 다른 배로 이동한 뒤에도 영구 추적하게 된다.
- Task 한 곳만 고치고 실제 Ability 시작 조건·경보·LOS 복구에 같은 실패 조건을 남기지 않는다.

현재 코드에서 직접 확인한 정지 경로는 분명하다. 다만 실제 관찰 장면에 인지 상실, Territory 이탈, 바닥 샘플 누락, BP 오버라이드나 BT Abort가 추가로 작용했는지는 PIE 기록이 필요하다. 구현은 첫 단계의 실행 진단을 기준으로 적용 범위를 확정하며, 계단 보행면 추가·공격 밸런스 변경·NavMesh 전환은 별도 범위로 남긴다.

## 8. 지속적인 난간 접지에 대한 상세 계획

### 8.1 기존 설명의 보완

난간에서는 Player의 CharacterMovement가 Walking이고 CurrentFloor가 Walkable일 수 있다. 그래도 AI의 `ResolveActorOnDeck`는 CurrentFloor 지지점 가까이에 갑판 그래프 노드가 있어야 성공한다. 난간 높이와 그래프 바닥 높이의 차이가 기본 MaximumStepHeight 45 cm보다 크거나, 난간 주변에 캡슐 여유를 만족하는 노드가 없으면 실패한다. 보조 탐색 아래 65 cm 한계도 영향을 줄 수 있다.

따라서 Player는 정상 접지 상태인데 AI는 해당 Player를 갑판 위치로 해석하지 못하는 것이 핵심이다. 같은 Player를 보는 여러 적이 각자 같은 판정에 실패하면 모두 멈춘 것처럼 나타날 수 있다. 이는 분석된 코드로 설명 가능한 경로이며 실제 전체 정지의 직접 원인은 실행 기록으로 확인한다.

1초 동안 마지막 위치를 쓰는 방식은 지속적인 난간 접지를 해결하지 못한다. 필요한 것은 **현재 난간 지지를 매번 확인해 유지하는 추적 상태**다.

### 8.2 세 가지 위치를 끝까지 분리한다

| 값 | 역할 | 보행 노드 필요 여부 |
| --- | --- | --- |
| 실제 Player 위치/지지점 | 시야, 조준, 실제 3D 거리, 피해, 함선 지지 증거 | 없음 |
| 갑판상의 추적 중심 | Player XY에 대한 접근·후퇴·측면 이동의 기준과 Surface 관계 | 중심의 XY에 유효 노드가 없어도 됨 |
| 적의 최종 목적지 | 실제 이동, 캡슐 여유, 도달 가능성, Claim | 반드시 검증된 바닥과 경로 필요 |

예를 들어 Player가 갑판보다 120 cm 높은 난간에 서 있다면 실제 높이는 그대로 유지한다. 추적 중심은 연관 갑판의 높이를 사용하고, 적의 목적지는 난간 기둥과 캡슐이 겹치지 않는 갑판 안쪽으로 정한다. 120 cm는 설명용 예시이며 현재 자산의 측정값은 아니다.

`ResolvePreciseLocalFloor`는 이동 위치에 요구되는 clearance까지 검사한다. 난간 바로 아래에서 이 함수가 실패해도 Player의 추적 중심까지 무효 처리하지 않는다. 추적 중심은 이동 핸들과 별도 타입이며, 주변 실제 목적지를 검증한 뒤 경로를 만든다.

### 8.3 난간 지지와 갑판 관계 확인

1. 기존 Player 자격·인지·Territory 정책을 확인한다.
2. CurrentFloor의 접지 상태, 지지점, 컴포넌트와 Movement Base를 읽는다. 캐릭터의 기존 HostShip 속성 하나만으로 실제 난간 지지를 확정하지 않는다.
3. 지지 컴포넌트가 해당 EnemyShip의 등록된 난간/장애물인지 확인한다. 별도 난간 Actor라면 명시적인 함선 등록이나 소유·부착 관계 검증이 필요하다. 다른 배·육지의 바닥을 받아들이지 않는다.
4. 난간 지지점 주변에서 제한된 수직·XY 범위와 실제 바닥 샘플을 이용해 연관 Surface 후보를 만든다. 아래층 Player 위에 위층 갑판이 있다는 이유로 위층을 선택하지 않는다. 갑판 내부/외곽 관계, 실제 충돌과 층 구획을 사용한다.
5. 이전 Surface는 연속성 힌트로만 사용한다. 최초 발견부터 난간 위인 경우도 현재 증거로 처리해야 하며, 난간을 따라 다른 층으로 이동하면 현재 증거로 관계를 갱신한다.
6. 같은 Mesh 컴포넌트에 위·아래층과 난간이 함께 있으면 컴포넌트 ID만으로 층을 정할 수 없다. 공간 질의로 구분되지 않는 구간에 한해 지원 구역/볼륨에 `AssociatedSurfaceId`를 지정하는 보조 설정을 추가한다. 이 설정은 추적 관계만 제공하며 물리 경로를 생성하지 않는다.
7. 지지가 현재 확인될 때마다 확인 시각과 XY를 갱신한다. 60초나 그 이상 서 있어도 현재 증거가 있으므로 추적 상태를 유지한다. 지지를 잃거나 다른 배로 옮기면 공중/이탈 정책으로 전환한다.

Surface 식별과 적별 도달 가능성을 분리한다. 아래층 적이 위층 난간의 Player를 본다고 해서 아래층으로 강제 투영하지 않는다. 동일한 타깃 해석이라도 각 적이 갈 수 있는 목적지는 자신의 연결 영역에 따라 달라진다.

### 8.4 난간 아래 수직 투영에만 의존하지 않는 목적지 탐색

추적 중심을 해석한 뒤 `GetReachableLocations`와 실제 바닥 검증을 사용한다.

1. 정상적인 거리 목표를 먼저 시도한다. 현재 방식처럼 Player–Enemy 선과 TargetDistance를 사용하되 갑판 기준 높이를 사용한다.
2. 목표가 난간 충돌·갑판 외곽·Claim·구멍 때문에 막히면, 난간 주변의 도달 가능한 갑판 후보를 제한 범위 안에서 검색한다. 정확한 한 점이 막혀도 주변 후보를 선택할 수 있어야 한다.
3. 후보는 연결 영역, Surface, 캡슐 여유, 전체 경로 지지, 실제 Pawn 충돌과 예약을 검증한다. 난간 Mesh를 Ignore해서 공간을 만들지 않는다.
4. 후보 점수는 목적에 맞는 거리 오차, 실제 Player를 향한 공격 LOS, 경로 길이, 기존 목적지 유지, 다른 적과의 점유를 고려한다. 타깃이 아래층인데 위층에서 보이는 후보를 무조건 높게 평가하지 않는다.
5. 난간 전용 fallback에서 거리 목표를 얼마나 완화할지 별도 허용 오차를 둔다. 근접은 최선의 안전 접근점, 원거리는 실제 사거리와 LOS를 만족하는 발사 위치를 우선한다. 원하는 거리 달성이 불가능하면 접근은 허용하되 공격 가능으로 간주하지 않는다.
6. 후보 평가와 최종 Claim/Route 교체를 분리한다. 불합격 후보를 평가할 때마다 기존 Route를 Clear하지 않는다. 새 Claim이 충돌하면 다음 후보를 시도한다.

Player가 난간을 따라 걸으면 로컬 XY 변화와 Surface 관계 변화에 따라 제한된 주기로 새 목적지를 선택한다. 배 자체가 움직이는 경우에는 동일 로컬 좌표를 현재 Transform으로 해석하며 배 월드 이동만으로 재탐색을 반복하지 않는다.

### 8.5 측면 이동·정지·재시도의 의미

갑판 가장자리에서는 원형 거리 띠의 한쪽 절반이 배 밖이 될 수 있다. 다음 정책을 둔다.

- 도달 가능한 좌우 후보만 선택하고 한쪽만 가능하면 그쪽을 사용한다.
- 거리 띠 전체 경로가 불가능하면 제한된 일반 접근 경로로 바꾸거나 현재 안전 위치에서 Focus를 유지한다. Player를 가로지르는 위험한 직선 이동으로 대신하지 않는다.
- 안전한 목적지에 이미 도착했으면 `HoldingPosition` 결과로 대기한다. 목적지가 없다는 Task 실패와 구분한다.
- 실패한 동일 목적지를 매 프레임 재선택하지 않는다. Player 이동, 점유 해제, 쿨다운 종료, LOS 변화, 제한된 재시도 주기에 반응한다.
- 여러 적은 Claim으로 서로 다른 접근 위치를 사용한다. 공간이 부족한 적은 관찰하며 대기하되 타깃 상태를 훼손하지 않는다.

난간 위 정지한 Player를 둘러싼 모든 근접 적이 언제나 움직여야 하는 것은 아니다. 안전한 접근점에 도착했고 무기가 닿지 않으면 관찰 대기가 정상이다. 수정 목표는 “난간에 올라간 순간 전부 경로를 버리고 얼어붙는 현상”과 “Player가 난간을 따라 이동해도 반응하지 않는 현상”을 없애는 것이다.

### 8.6 공격과 보스 패턴

근접/보스 기본 공격은 현재 난간 지지를 같은 갑판과 연관된 타깃으로 인정할 수 있게 하되, 실제 Player 높이와 3D 거리, LOS, 무기 타격 창의 실제 충돌을 유지한다. 투영 좌표를 실제 피해 위치로 사용하지 않는다. 높아서 무기가 닿지 않으면 공격 불가이며 추적 실패와는 다른 결과다.

원거리는 현재 난간 위의 실제 조준점에 대해 최소·최대 사거리와 LOS를 검사한다. 난간이 막으면 안전한 측면/발사 위치를 선택한다. 피할 수 없는 차폐는 관찰 결과로 처리하고, 기존 3초 LOS 복구 만료가 현재 확인된 난간 타깃을 무조건 버리지 않도록 복구 실패와 인지 상실을 분리한다. 이 예외는 난간의 현재 지지와 인지·영역 조건이 유지되는 동안에만 적용한다.

보스 Walk·Strafe는 동일 추적 해석을 사용한다. Dash는 타깃 방향을 계산할 수 있어도 지지 바닥·경로·종점 조건이 없으면 실행하지 않는다. Vanish는 난간 위가 아니라 기존 정책상 보스가 이동 가능한 갑판의 안전한 앞/뒤 후보를 사용한다. 안전 후보가 없는 스킬은 건너뛰고 접근·관찰로 전환한다. 확정 스킬의 목적지와 사망 시 Freeze 계약은 기존대로 유지한다.

### 8.7 이번 보완의 구현·검증 순서

1. 실제 난간에서 MovementMode, CurrentFloor 지지 컴포넌트·점, 그래프 노드 실패 이유와 각 적의 Task 실패를 함께 기록한다. 난간 위에 60초 이상 머물며 재현한다.
2. 추적 결과 타입에 지속적인 난간 지지 상태를 추가하고 HostShip·Surface 관계를 구현한다. 처음부터 난간 위인 타깃도 처리한다.
3. 갑판 추적 중심과 실제 목적지를 분리하고 난간 주변의 도달 가능한 후보 탐색을 구현한다.
4. 일반 적 Navigation·Task·경로/Claim 교체를 적용한다. `HoldingPosition`과 일시 실패, 진짜 타깃 무효를 분리한다.
5. 보스 Selector·Strafe·Snapshot과 공격 시작 조건, 경보·LOS 복구를 같은 정책에 맞춘다.
6. 현재 연결된 BT에 관찰·제한 재시도를 반영하고 Editor 빌드·핵심 회귀·PIE·서버/두 클라이언트를 검증한다.

추가 수용 기준은 다음과 같다.

- 난간에 60초 이상 서 있어도 기억 유예 만료로 타깃을 잃지 않는다.
- 난간을 따라 이동할 때 Melee/Ranged/Boss가 안전한 새 접근점 또는 공격점에 반응한다.
- 첫 발견부터 난간 위이고 마지막 갑판 위치가 없어도 처리한다.
- 수직으로 내려온 위치에 노드가 없어도 근처 갑판 후보를 찾는다.
- 높은 난간, 배 외곽, 겹치는 위·아래층, 같은 Mesh의 여러 난간, 별도 난간 Actor에서 다른 배·다른 층을 오인하지 않는다.
- 모든 적이 같은 후보를 선택해 겹치지 않으며, 대기 중인 적은 이후 Player 이동과 공간 변화에 반응한다.
- 적이 난간에 올라가거나 갑판 밖으로 나가지 않고, 투영된 Player 위치에 가짜 피해를 주지 않는다.
- 난간을 떠나 다른 배·바다로 이동하거나 인지·영역 조건을 잃으면 기존 이탈 정책이 정상 적용된다.
